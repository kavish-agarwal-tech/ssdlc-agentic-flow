CODING AGENT IMPLEMENTATION PROMPT
==================================

Project: Governed Agentic SSDLC / SDLC Engineering System

PRIMARY GOAL
------------
Build the reusable agentic software-engineering orchestration platform FIRST.

Do NOT begin by manually implementing the URL shortener.

The URL shortener will later be used as the first workload to prove that this SSDLC system can take a requirement through the complete software-development lifecycle using the same governed orchestration engine.

The implementation must be professional, reviewable, auditable, and suitable for a public GitHub repository used in a software-engineering interview.

======================================================================
1. ASSIGNMENT CONTEXT
======================================================================

This system is being created for an engineering interview exercise whose central objective is to demonstrate an agentic execution model capable of transforming a requirement into a reviewable engineering outcome.

The broader assignment expects the solution to demonstrate:

- requirement understanding;
-- ambiguity detection;
- task decomposition;
- brownfield codebase reasoning;
- architecture and design;
- implementation;
- testing;
- documentation;
- release readiness;
- explicit dependency graphs;
- non-linear and stateful execution;
- parallel and sequential paths;
- synchronization;
- human approval checkpoints;
- bounded retries;
- fallback;
- rollback;
- safe-stop behavior;
- cross-stage context preservation;
- decision lineage;
- governance and policy guardrails;
- audit-grade traceability;
- reliability metrics;
- dynamic re-planning;
- controlled agent autonomy;
- final human oversight.

The platform must be reusable for:
- greenfield work;
- brownfield enhancements/refactors/bug fixes;
- ambiguous requirements;
- testing/documentation improvements.

The URL-shortener requirement will be used after the SSDLC platform is working to demonstrate all of the above.

======================================================================
2. CORE DESIGN PRINCIPLE
======================================================================

Design and implement around this principle:

    REASONING IS PROBABILISTIC; CONTROL IS DETERMINISTIC.

Agents may:
- interpret;
- reason;
- propose;
- critique;
- diagnose;
- generate;
- recommend;
- explain.

The orchestrator must deterministically control:
- state transitions;
- dependency satisfaction;
- entry gates;
- exit gates;
- approval requirements;
- retry limits;
- review-loop limits;
- artifact versioning;
- invalidation;
- synchronization;
- policy enforcement;
- deterministic tool execution;
- test pass/fail;
- build pass/fail;
- release-readiness evaluation;
- rollback;
- safe-stop;
- audit persistence.

An LLM must never be allowed to simply claim:
- tests passed;
- build succeeded;
- a gate passed;
- a security issue is resolved;
- an artifact is approved.

These must be supported by deterministic state, evidence, policy, or explicit human approval.

======================================================================
3. FRAMEWORK DECISION: LANGGRAPH
======================================================================

Use LangGraph as the primary orchestration framework unless a concrete blocking reason is discovered during implementation.

Do NOT custom-build a workflow engine when a mature framework already provides the orchestration primitives required by this system.

Document professionally why LangGraph was selected.

The reasoning must include:

1. The workflow is a graph, not a simple linear prompt chain.
2. It requires conditional routing.
3. It requires loops.
4. It requires bounded retries.
5. It requires parallel branches.
6. It requires synchronization.
7. It requires long-running state.
8. It requires human-in-the-loop interrupts.
9. It requires safe resume after human input.
10. It requires checkpointing/persistence.
11. It requires dynamic routing after failures or upstream changes.
12. It provides standard orchestration primitives instead of forcing custom infrastructure.
13. Governance logic remains application-owned.

Explicitly document the boundary:

LangGraph provides:
- graph execution;
- state propagation;
- conditional edges;
- checkpointing;
- interrupts;
- resumability;
- parallel execution primitives;
- graph lifecycle.

Our application owns:
- SSDLC domain state;
- requirements lifecycle;
- artifact versioning;
- approval policy;
- review finding lifecycle;
- retry budgets;
- severity rules;
- artifact invalidation;
- audit semantics;
- human governance policy;
- release policy;
- safe-stop rules;
- rollback policy;
- metrics semantics;
- deterministic tool policy.

Do not make "we use LangGraph" the architecture.

LangGraph is an implementation framework serving a framework-independent architecture.

5. REQUIREMENT ANALYSIS AGENT
======================================================================

Create a Requirement Analysis Agent.

Its job is not to summarize the requirement.

It must:

- understand intent;
- normalize the request;
- identify ambiguity;
- identify contradictions;
- identify missing acceptance criteria;
- identify missing invariants;
- identify source-of-truth questions;
- identify authoritative record ownership;
- identify missing functional requirements;
- identify missing non-functional requirements;
- identify missing performance expectations;
- identify availability expectations;
- identify reliability expectations;
- identify scalability expectations;
- identify observability requirements;
- identify security requirements;
- identify retention requirements;
- identify compliance/change-control concerns;
- identify hidden assumptions.

It must classify uncertainty as:

- BLOCKING_AMBIGUITY
- NON_BLOCKING_AMBIGUITY
- PROPOSED_DEFAULT
- ASSUMPTION_REQUIRING_APPROVAL

When human input is needed, do not ask weak questions.

For every question provide:

- what is unclear;
- why it matters;
- plausible options;
- recommendation, where appropriate;
- reasoning behind the recommendation;
- explicit indication that recommendation is non-binding;
- request for human confirmation.

Example:

Ambiguity:
Default URL expiration is not defined.

Why it matters:
It affects redirect semantics, data lifecycle, cleanup, analytics retention,
storage growth, and API behavior.

Options:
A. No default expiration.
B. 30-day default.
C. Configurable default.

Recommendation:
Option A for MVP because it avoids implicit lifecycle behavior.

Decision:
Human confirmation required.

The agent must not silently resolve blocking ambiguity.

======================================================================
10. BOUNDED ARCHITECTURE REVIEW LOOP
======================================================================

Architecture Author and Architecture Reviewer may iterate.

Default maximum:
- 3 autonomous review/revision cycles.

Each cycle must persist:
- findings;
- responses;
- architecture version changes;
- disposition.

Exit conditions:

- zero unresolved BLOCKER items;
- zero unresolved HIGH items unless policy/human accepts risk;
- review marked complete;
- required artifacts present.

If maximum cycles are exhausted:

- SAFE STOP;
- escalate to human;
- present unresolved findings;
- present recommendation/options;
- await decision.

Never allow uncontrolled agent-to-agent chat loops.

The orchestrator mediates each cycle.

22. FAILURE ANALYSIS AND TARGETED RE-PLANNING
======================================================================

If tests fail, invoke Failure Analysis Agent.

Classify likely root cause:

- IMPLEMENTATION_DEFECT
- TEST_DEFECT
- LLD_DEFECT
- ARCHITECTURE_DEFECT
- REQUIREMENT_DEFECT
- ENVIRONMENT_OR_TOOLING

Produce:
- evidence;
- reasoning;
- recommended route.

Orchestrator routes back to the appropriate node.

Examples:

implementation -> Coding
test defect -> Test Design
LLD defect -> LLD
architecture defect -> Architecture flow
requirement defect -> Requirement flow
tool/environment -> tool recovery/human

Do NOT simply ask Coding Agent to try again.

Bound re-plan/retry attempts.

When retry budget is exhausted:
- SAFE STOP;
- persist evidence;
- request human decision.

======================================================================
23. ARTIFACT DEPENDENCY AND INVALIDATION
======================================================================

Implement explicit artifact lineage.

Example:

Requirement v3
  -> Architecture v2
      -> Plan v1
          -> LLD v4
              -> Code v7
              -> Tests v5
                  -> Release Candidate v2

When an upstream approved artifact changes, downstream artifacts must be marked:

- VALID;
- REVALIDATE;
- INVALIDATED;
- SUPERSEDED;

depending on impact.

Example:
Technology ADR changes Python -> Java.

Expected effect:

Requirements: VALID
Logical architecture: VALID or REVALIDATE
Technology ADR: CHANGED
Plan: REVALIDATE
LLD: INVALIDATED
Code: INVALIDATED
Tests: INVALIDATED
Release package: INVALIDATED

Do not reset unrelated work unnecessarily.

This is a key demonstration of dynamic replanning.
