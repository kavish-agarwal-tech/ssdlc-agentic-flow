REFACTOR PROMPT — MAKE MOCK/DETERMINISTIC MODE THE PRIMARY SUBMISSION PATH

Project: Governed Agentic SSDLC
Repository: kavish-agarwal-tech/ssdlc-test

GOAL
----

Simplify the current implementation so the assignment can be completed and
demonstrated reliably.

Do NOT rewrite the project from scratch.

The new default should be:

    deterministic/mock agent execution for the core assignment demo

while preserving:

    optional DeepSeek support as an extension

The core submission must not depend on:
- external LLM availability
- API keys
- network access
- probabilistic outputs

The assignment should still demonstrate real:
- LangGraph orchestration
- stateful execution
- conditional routing
- parallel branches
- synchronization
- human approval
- bounded retries
- safe stop
- artifact lineage
- dynamic replanning
- auditability
- actual tests/build
- greenfield, brownfield and ambiguous scenarios

==================================================

For the default deterministic mode, agents are specialized engineering workers
with explicit responsibilities and structured contracts.

They may be implemented using deterministic logic, fixtures or bounded templates.

Do not pretend mock output is generated by a real LLM.

Clearly label:

    MOCK / DETERMINISTIC MODE

and:

    OPTIONAL REAL-LLM MODE

The core architecture remains agentic because multiple specialized workers
operate under stateful orchestration, bounded autonomy, human gates, retry,
replanning and validation.

==================================================
5. REQUIREMENT AGENT — DETERMINISTIC BEHAVIOR
==================================================

This is especially important.

In mock/default mode, requirement analysis must be deterministic and must not
generate endless architecture questions.

Classify uncertainty into:

A. PRODUCT_AMBIGUITY
B. ARCHITECTURE_DECISION
C. NON_BLOCKING_ASSUMPTION

Only PRODUCT_AMBIGUITY may require human clarification.

Examples of PRODUCT_AMBIGUITY:
- Are links permanent or expiring?
- Is authentication required?
- Is deletion supported?
- Should duplicate URLs deduplicate?
- Must analytics be exact or best-effort?
- What should happen after expiry?

Examples that MUST NOT block requirements:
- SQLite vs file
- 302 vs 307
- Base62 vs UUID
- /r/{code} vs /{code}
- sync vs async analytics implementation
- module names
- framework choice
- package structure
- thread/process model

Those belong to architecture/design.

For the greenfield URL-shortener scenario, the deterministic requirement agent
should normally produce zero or very few blocking questions.

For the ambiguous expiration scenario, it SHOULD produce blocking questions.

7. MOCK GREENFIELD SCENARIO
==================================================

The deterministic greenfield run must generate a real working URL shortener.

It must produce:

- application source
- tests
- package/build metadata
- release-readiness documentation

The output must NOT be another greeting fixture.

Create a real deterministic URL-shortener fixture/generator.

The generated app must at minimum support:

POST /links
GET /r/{code}
GET /links/{code}/analytics
GET /health

SQLite may be used for persistence.

Use whatever exact route prefix is simplest and consistent.

The generated solution must pass actual tests and build/package successfully.

==================================================
8. MOCK AMBIGUOUS SCENARIO
==================================================

Use this input:

    "Add expiration support."

The deterministic Requirement Agent must detect genuine ambiguity and pause.

It should ask a small number of relevant questions, for example:

- Is expiration optional or mandatory?
- Is there a default TTL?
- What response should an expired link return?
- Should expired links be deleted or retained?

Do not ask implementation questions such as:
- table schema
- scheduler implementation
- cache strategy
- framework selection

After human answers, resume the same workflow.

This scenario demonstrates HITL and requirement evolution.

==================================================
9. MOCK BROWNFIELD SCENARIO
==================================================

Start from the previously generated URL-shortener source.

Use a change request such as:

    "Add daily click analytics."

The brownfield analysis must inspect the existing codebase and identify:
- affected modules/files
- persistence impact
- API impact
- test impact
- regression risk

Then continue through:
- planning/design
- code/test generation
- shared review
- real validation
- release readiness

Do not use a separate hard-coded workflow.

==================================================
10. CODE AND TEST GENERATION
==================================================

Keep code and test generation as separate parallel branches.

In deterministic mode:
- Coding Agent should generate valid source for the current slice.
- Test Design Agent should generate valid tests from the approved requirement/design.
- Test Design must not receive implementation source as its primary contract.

Preserve the existing independence property.

The generated code and tests may come from templates/fixtures in mock mode.

That is acceptable.

They must still be real files and actual pytest must run.

==================================================
11. QUALITY REVIEW
==================================================

Keep one shared Quality Review after code/test synchronization.

In mock/default mode, this may be deterministic rule-based review.

Check:
- requirement coverage
- expected files present
- expected tests present
- forbidden files absent
- basic API/design alignment
- obvious missing acceptance coverage
- no unresolved deviations

Do not build elaborate mock reviewer behavior.

==================================================
12. FAILURE ANALYSIS
==================================================

Keep failure analysis, but deterministic mode may classify common failures using
simple rules.

Examples:

pytest failure in application behavior
    -> IMPLEMENTATION_DEFECT

test import/path mismatch
    -> DESIGN_DEFECT or TEST_DEFECT

missing dependency/tool
    -> ENVIRONMENT_OR_TOOLING

The purpose is to demonstrate targeted routing, not AI diagnosis quality.

22. FINAL DESIGN STORY
==================================================

The implementation and README should support this explanation:

    "I separated agent behavior from orchestration behavior. The default evaluator
    path uses deterministic agent implementations so the assignment is fully
    reproducible and does not depend on an external model. LangGraph still provides
    real stateful orchestration, parallel execution, human interrupts, retry,
    synchronization and recovery.

    The same provider boundary also supports DeepSeek as an optional real-LLM mode,
    showing how reasoning can be made probabilistic without making the control
    plane probabilistic.

    For the assignment I optimized for reliable demonstration of controlled
    autonomy rather than external-model dependency."

Most important instruction:

STOP EXPANDING THE PLATFORM.

Make the three assignment scenarios work cleanly and reproducibly, then polish
the submission.
