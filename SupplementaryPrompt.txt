SUPPLEMENTARY REFACTORING PROMPT
================================

Project: Governed Agentic SSDLC
Repository: kavish-agarwal-tech/ssdlc-test

CONTEXT
-------

The current repository already contains a working Python/LangGraph-based
Agentic SSDLC implementation.

Do NOT rewrite the project from scratch.

The current implementation has strong foundations:

- LangGraph stateful orchestration
- SQLite checkpoint/resume
- human interrupts
- versioned artifacts
- artifact dependency/invalidation
- typed Pydantic contracts
- real LLM integration
- MockProvider for deterministic tests
- architecture review loops
- parallel code and test-design branches
- deterministic test/build execution
- failure analysis
- brownfield reasoning
- audit events
- workflow metrics
- safe-stop behavior

However, the current implementation is somewhat over-engineered for the
interview assignment.

The goal of this refactor is:

    SIMPLIFY THE IMPLEMENTATION WITHOUT LOSING THE ASSIGNMENT'S
    CRITICAL AGENTIC AND GOVERNANCE CAPABILITIES.

The resulting system should be easy for an interviewer to understand in
approximately five minutes.

Do not optimize for building a generic enterprise SSDLC platform.

Optimize for a convincing, runnable interview prototype.

======================================================================
1. PRIMARY ARCHITECTURAL PRINCIPLE
======================================================================

Preserve:

    REASONING IS PROBABILISTIC.
    CONTROL IS DETERMINISTIC.

The real LLM may:

- interpret requirements
- detect ambiguity
- propose architecture
- critique architecture
- plan implementation
- generate code
- generate tests
- review engineering artifacts
- diagnose failures
- prepare release-readiness summaries

The LLM must NOT control:

- workflow state transitions
- approvals
- retry budgets
- graph routing policy
- artifact validity
- test pass/fail
- build pass/fail
- release-gate decisions
- safe-stop decisions
- audit persistence

Those remain deterministic application responsibilities.

======================================================================
2. LLM PROVIDER STRATEGY
======================================================================

REMOVE Ollama-specific support.

The current real LLM path should use:

    DeepSeekProvider

Retain:

    MockProvider

The intended provider model is:

                    Provider
                       |
            +----------+----------+
            |                     |
            v                     v
      DeepSeekProvider        MockProvider
      real reasoning          deterministic tests

DeepSeek is the primary real-agent provider.

MockProvider exists for:

- unit tests
- workflow tests
- deterministic CI
- failure-path simulation
- bounded-review tests
- safe-stop tests
- human-interrupt tests

Do NOT use mocked LLM output as the primary URL-shortener demonstration.

The URL-shortener workflow should normally run using DeepSeek so requirement
analysis, architecture reasoning, ambiguity detection, planning, review and
failure analysis are genuinely model-driven.

The mock path must remain capable of proving orchestration without network/API
dependency.

Do not add additional model providers unless they are already trivial and
require essentially zero maintenance.

Remove unnecessary documentation and implementation for:

- Ollama
- local model discovery
- Ollama health checks
- unused provider options

If a generic Provider interface already exists, KEEP IT.

Do not redesign the provider layer unnecessarily.

======================================================================
4. REMOVE PLAN APPROVAL
======================================================================

Remove the normal mandatory:

    plan_approval

human gate.

Current conceptual behavior:

Architecture Approval
       |
    Planning
       |
 Plan Approval
       |
      LLD

Change to:

Architecture Approval
       |
       v
 Planning + LLD

Reason:

The human has already approved:

- requirements
- architecture
- technology decisions

Planning within those boundaries should be autonomously executable.

Human intervention is required only if planning discovers:

- new functional scope
- unresolved requirement ambiguity
- architecture-impacting conflict
- significant risk requiring acceptance

In those cases, route back appropriately.

Do not require routine approval of every generated plan.

Remove tests, CLI behavior and documentation whose sole purpose is enforcing
normal plan approval.

======================================================================
5. COMBINE PLANNING AND LLD
======================================================================

Combine the current separate Planning Agent and LLD Agent into one logical:

    PlanningDesign Agent

or equivalent.

It should produce:

- vertical slices
- dependencies
- sequencing
- acceptance criteria
- requirement mapping
- risks
- module/component structure
- interfaces
- API contracts
- persistence decisions
- validation behavior
- error behavior
- observability expectations
- test seams
- implementation notes

Do not eliminate vertical slices.

The purpose is simply to avoid making planning and LLD two expensive,
independent reasoning stages when one structured model response can produce
both for this prototype.

A suitable artifact might conceptually contain:

EngineeringPlan:
    slices[]
    rationale

Slice:
    id
    title
    dependencies
    requirement_refs
    acceptance_criteria
    design
    validation
    risks

Design:
    modules
    interfaces
    contracts
    persistence
    validation
    errors
    observability
    test_seams

Adapt current models rather than introducing unnecessary new frameworks.

6. KEEP CODE AND TEST DESIGN PARALLEL
======================================================================

Do NOT remove this capability.

It is one of the strongest demonstrations of real non-linear orchestration.

After Planning/Design:

                 Approved Design
                     /      \
                    /        \
                   v          v
               Coding     Test Design
                   \          /
                    \        /
                     v      v
                       Join

Both branches must consume the same authoritative:

- requirement
- architecture
- ADRs
- slice
- design
- acceptance criteria

The Test Design Agent must continue to be independent.

Do NOT provide generated production code to the Test Design Agent.

Preserve the existing test proving this isolation.

This is a key interview talking point:

    "Tests derive independently from the approved specification rather than
    reproducing the generated implementation's assumptions."

7. SIMPLIFY CODE/TEST REVIEW
======================================================================

The existing code-review and test-review subgraphs are more elaborate than
required.

Replace:

    Code -> Code Review loop

and

    Tests -> Test Review loop

with one:

    Quality Review Agent

AFTER code/test synchronization.

Quality Review should assess both artifacts against the authoritative
requirements and design.

Review:

- requirement alignment
- acceptance-criteria coverage
- implementation correctness
- API/design alignment
- maintainability
- input validation
- security basics
- secrets/logging safety
- error handling
- meaningful test assertions
- negative cases
- edge/boundary cases
- excessive mocking
- reliability considerations
- obvious deviations

Continue using structured findings:

- BLOCKER
- HIGH
- MEDIUM
- LOW

Do not implement another generalized review framework.

Reuse the existing Finding model where practical.

11. KEEP FAILURE ANALYSIS, BUT SMALL
======================================================================

Retain Failure Analysis.

It is useful because failed deterministic validation should not blindly route
back to Coding.

Continue classifying failures such as:

- IMPLEMENTATION_DEFECT
- TEST_DEFECT
- DESIGN_DEFECT
- ARCHITECTURE_DEFECT
- REQUIREMENT_DEFECT
- ENVIRONMENT_OR_TOOLING

Simplify LLD-related routing if Planning + LLD have been combined.

For example:

Implementation defect
    -> Coding

Test defect
    -> Test Design

Design defect
    -> Planning/Design

Architecture defect
    -> Architecture

Requirement defect
    -> Requirement

Environment/tooling
    -> retry/safe-stop/human

Maintain bounded retries.

Do not create complex generalized remediation infrastructure.

======================================================================
12. KEEP ARTIFACT VERSIONING AND INVALIDATION
======================================================================

The current artifact lineage implementation is valuable and directly supports
dynamic replanning.

Keep it.

Do NOT expand it into a generalized dependency-management platform.

A simple dependency chain is enough:

Requirement
   |
Architecture
   |
Plan/Design
   |
Code + Tests
   |
Release

Examples:

Requirement changes:
    invalidate architecture, plan/design, code, tests, release.

Architecture changes:
    retain requirement;
    invalidate plan/design, code, tests, release.

Plan/design changes:
    invalidate code, tests, release.

Implementation changes:
    invalidate relevant validation/release artifacts.

Preserve unaffected artifacts where practical.

28. REFACTORING METHOD
======================================================================

Do not make one giant rewrite.

Before changing code, produce a short inventory:

KEEP
SIMPLIFY
MERGE
REMOVE/DEFER

Then refactor incrementally.

Recommended sequence:

STEP 1
Remove Ollama code/docs and make DeepSeek the only real provider.

STEP 2
Remove normal plan approval.

STEP 3
Combine planning and LLD.

STEP 4
Preserve parallel Coding/Test Design but combine their review paths into one
Quality Review stage.

STEP 5
Merge Documentation into Release Readiness.

STEP 6
Reduce architecture review default to two iterations.

STEP 7
Simplify graph diagram and routing.

STEP 8
Run full workflow test suite.

STEP 9
Remove obsolete tests/code/docs.

STEP 10
Run formatting/lint/tests/build.

STEP 11
Update README and architecture documentation.

STEP 12
Run the URL-shortener greenfield workflow using DeepSeek.

Do not delete working code until replacement behavior passes tests.

29. SUCCESS CRITERIA
======================================================================

The refactor is successful when:

- LangGraph remains the orchestrator.
- DeepSeek is the real LLM provider.
- MockProvider supports deterministic tests.
- Ollama has been removed.
- the graph fits cleanly on one diagram.
- approximately three normal human gates remain.
- architecture review remains independent and bounded.
- code and test generation remain genuinely parallel.
- test design does not consume implementation code.
- actual tools determine test/build success.
- failure analysis can route backward.
- dynamic artifact invalidation still works.
- safe-stop behavior remains.
- brownfield reasoning remains.
- auditability remains sufficient to explain the run.
- repository setup is simpler.
- documentation is shorter and clearer.
- URL-shortener can be produced using a real DeepSeek workflow.
- mock mode works without external LLM access.

Most importantly:

The repository should look like a deliberate interview solution,
not an attempt to build an entire commercial SSDLC platform.

======================================================================
30. INTERVIEW DESIGN STORY
======================================================================

Ensure the implementation and README support this explanation:

    "I used LangGraph rather than building a custom orchestration engine because
    the problem requires stateful graph execution, conditional routing, parallel
    branches, synchronization, human interrupts and resumability.

    I use DeepSeek for probabilistic engineering reasoning, while workflow
    control, approvals, retry limits, artifact state, test execution and release
    gates remain deterministic.

    I deliberately kept a deterministic MockProvider so the orchestration itself
    can be reliably tested without depending on model availability.

    I also deliberately scoped the implementation to the assignment rather than
    building a generalized enterprise SSDLC platform."

That engineering judgment is a key part of the solution.
